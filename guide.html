1Start the platform

From the project root (skip the first command if the network already exists):

docker network create lakehouse
docker compose -f processing/docker-compose.yml up -d --build
docker compose -f streaming/docker-compose.yml up -d --build
docker compose -f orchestration/docker-compose.yml up -d --build
Expected: no errors; first build takes a few minutes, later starts are seconds.

2Check all containers

docker ps --format "{{.Names}}: {{.Status}}"
Expected — 7 running containers: spark-master, iceberg-rest, minio (healthy), kafka (healthy), order-events-producer, airflow-webserver, airflow-scheduler, plus airflow-db (healthy). The *-init containers exit with code 0 — that is normal, they are one-shot setup jobs.

3Kafka & producer

The producer emits order lifecycle events (created → paid → shipped → completed) around the clock:

docker logs --tail 5 order-events-producer
Expected: lines like 150 events sent (last: ORD-S… shipped at …).

Read messages straight from the topic:

docker exec kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic orders_events --from-beginning --max-messages 3 --timeout-ms 15000
Expected: 3 JSON events with event_id, order_id, status, event_time.

4Airflow & the two DAGs

  1. Open http://localhost:8090 and log in with admin / admin.
  2. You should see two DAGs: batch_etl and streaming_supervisor.
  3. Unpause both with the toggle on the left.
  4. Trigger streaming_supervisor first (▶ button), then trigger batch_etl.
Expected: streaming_supervisor goes green in ~30 s (2 tasks: check_processing_container → ensure_streaming_job_running). batch_etl goes green in ~5–6 min (7 tasks: load_batch_sources → dq_bronze → bronze_to_silver → dq_silver → silver_to_gold → dq_gold → great_expectations_validation).
Note: every task runs spark-submit inside the spark-master container via docker exec — open any task log in the Airflow UI and you can see it; no Spark runs on the Airflow containers.

5Streaming into bronze

After streaming_supervisor has run once, the streaming job appends Kafka events to Iceberg every 30 s:

docker exec spark-master tail -n 5 /tmp/streaming_ingest.log
Expected: recent log lines; look for Committed snapshot entries (Iceberg commits).
docker exec spark-master spark-submit --master "local[*]" /opt/spark/jobs/show_tables.py bronze
Expected: customers_raw (500), products_raw (100), orders_raw (5001), and order_events with a growing count — run it twice a minute apart and the number goes up. That is the live stream landing in the lake.

6Batch run & the layers

After a green batch_etl run, inspect silver and gold:

docker exec spark-master spark-submit --master "local[*]" /opt/spark/jobs/show_tables.py silver
docker exec spark-master spark-submit --master "local[*]" /opt/spark/jobs/show_tables.py gold
Expected silver: customers (500), products (100), orders (~5600+, growing with the stream), order_events, order_events_rejected.
Expected gold: dim_customer, dim_product (100), dim_date (365), fact_orders (same count as silver orders), daily_sales.
Data cleaning proof: bronze orders_raw has 5001 rows but silver has fewer from batch — the seed data deliberately contains a negative quantity, a missing customer id, a negative amount and a duplicate order id; silver drops them all.

7Late-data handling (48h rule)

The producer intentionally sends ~15% events 1–47 h old (must be accepted) and ~5% events older than 48 h (must be quarantined):

docker exec spark-master spark-submit --master "local[*]" /opt/spark/jobs/show_tables.py silver
Expected: silver.order_events_rejected is non-empty; every row has lateness_hours > 48 and reason "arrived more than 48h after event_time". In silver.order_events all rows have lateness_hours ≤ 48.

8SCD2 demo (customer dimension history)

  1. In Airflow open batch_etl → ▶ → Trigger DAG w/ config.
  2. Paste {"snapshot": "day2"} and trigger. Day 2 contains ~40 customers who moved city or changed segment.
  3. When the run is green:
docker exec spark-master spark-submit --master "local[*]" /opt/spark/jobs/show_tables.py gold
Expected: gold.dim_customer grows to 540 rows — 500 current (is_current = true) and 40 closed historical versions with effective_to filled. Old orders keep pointing at the historical version (that is the point of SCD Type 2).

9Data quality & Great Expectations

docker exec spark-master spark-submit --master "local[*]" /opt/spark/jobs/show_tables.py audit
Expected: audit.dq_results — one row per check per run (bronze checks include WARN findings for the planted dirty rows; silver/gold checks all passed = true). audit.ge_results — 15 Great Expectations results per run, all success = true.
Negative test (optional): the DQ gates really block — if a silver ERROR check ever fails, the DAG stops before gold and the task shows the failing check name in its log.

10MinIO files (the physical lake)

  1. Open http://localhost:9001, log in admin / password.
  2. Browse the warehouse bucket.
Expected: folders per namespace (bronze, silver, gold, audit), each table with data/ (parquet files) and metadata/ (Iceberg snapshots/manifests).

Troubleshooting

"network lakehouse not found" — run docker network create lakehouse, then the three up commands again.

Airflow shows no DAGs yet — wait ~20 s after startup; the scheduler rescans DAGs every 10 s.

order_events count not growing — trigger streaming_supervisor once and check docker exec spark-master tail -n 30 /tmp/streaming_ingest.log.

Spark jobs fail with Service failed: 500 after a Docker/PC restart — the Iceberg catalog can come back in a bad state after an unclean shutdown. Run docker restart iceberg-rest, then re-trigger the DAG. If the streaming job died during the outage, streaming_supervisor restarts it automatically on its next 10-minute run.

Port already in use — something on your machine holds 8090 / 9000 / 9001 / 8181 / 29092; stop it or change the published port in the relevant compose file.

After a reboot — just run the three docker compose … up -d commands again; all data survives in Docker volumes.

Shutdown

docker compose -f orchestration/docker-compose.yml down
docker compose -f streaming/docker-compose.yml down
docker compose -f processing/docker-compose.yml down
Note: add -v to also wipe the data volumes (fresh start next time). The credentials in this guide are local development defaults — fine for the demo, never for production.
