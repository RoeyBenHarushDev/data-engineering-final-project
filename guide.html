1הפעלת המערכת

מתיקיית שורש הפרויקט (אפשר לדלג על הפקודה הראשונה אם הרשת כבר קיימת):

docker network create lakehouse
docker compose -f processing/docker-compose.yml up -d --build
docker compose -f streaming/docker-compose.yml up -d --build
docker compose -f orchestration/docker-compose.yml up -d --build
תוצאה צפויה: ללא שגיאות; ה־build הראשון לוקח כמה דקות, הפעלות חוזרות לוקחות שניות.

2בדיקת כל הקונטיינרים

docker ps --format "{{.Names}}: {{.Status}}"
תוצאה צפויה — 7 קונטיינרים רצים: spark-master, iceberg-rest, minio (healthy), kafka (healthy), order-events-producer, airflow-webserver, airflow-scheduler, ובנוסף airflow-db (healthy). קונטיינרים בשם *-init מסיימים עם קוד 0 — זה תקין, הם משימות הקמה חד־פעמיות.

3Kafka וה־Producer

ה־Producer שולח אירועי מחזור חיים של הזמנות (created ← paid ← shipped ← completed) באופן רציף:

docker logs --tail 5 order-events-producer
תוצאה צפויה: שורות כמו 150 events sent (last: ORD-S… shipped at …).

קריאת הודעות ישירות מה־Topic:

docker exec kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic orders_events --from-beginning --max-messages 3 --timeout-ms 15000
תוצאה צפויה: שלושה אירועי JSON עם event_id, order_id, status, event_time.

4Airflow ושני ה־DAGs

  1. פותחים את http://localhost:8090 ומתחברים עם admin / admin.
  2. אמורים להופיע שני DAGs: batch_etl ו־streaming_supervisor.
  3. מפעילים את שניהם באמצעות המתג בצד.
  4. מריצים קודם את streaming_supervisor (כפתור ▶), ואחר כך את batch_etl.
תוצאה צפויה: streaming_supervisor נהיה ירוק תוך כ־30 שניות (2 משימות: check_processing_container ← ensure_streaming_job_running). batch_etl נהיה ירוק תוך כ־5–6 דקות (7 משימות: load_batch_sources → dq_bronze → bronze_to_silver → dq_silver → silver_to_gold → dq_gold → great_expectations_validation).
הערה: כל משימה מריצה spark-submit בתוך הקונטיינר spark-master באמצעות docker exec — אפשר לראות זאת בלוג של כל משימה בממשק Airflow; אף תהליך Spark לא רץ על הקונטיינרים של Airflow.

5הזרמת נתונים ל־Bronze

אחרי ריצה אחת של streaming_supervisor, ה־Job של הסטרימינג כותב אירועים מ־Kafka ל־Iceberg כל 30 שניות:

docker exec spark-master tail -n 5 /tmp/streaming_ingest.log
תוצאה צפויה: שורות לוג עדכניות; חפשו שורות Committed snapshot (קומיטים ל־Iceberg).
docker exec spark-master spark-submit --master "local[*]" /opt/spark/jobs/show_tables.py bronze
תוצאה צפויה: customers_raw (500), products_raw (100), orders_raw (5001), וטבלת order_events עם מונה שגדל — הריצו פעמיים בהפרש דקה והמספר יעלה. זה הסטרים החי שנוחת ב־Lake.

6ריצת Batch ושכבות הנתונים

אחרי ריצה ירוקה של batch_etl, בודקים את שכבות ה־Silver וה־Gold:

docker exec spark-master spark-submit --master "local[*]" /opt/spark/jobs/show_tables.py silver
docker exec spark-master spark-submit --master "local[*]" /opt/spark/jobs/show_tables.py gold
צפוי ב־Silver: customers (500), products (100), orders (בגדילה מתמדת עם הסטרים), order_events, order_events_rejected.
צפוי ב־Gold: dim_customer, dim_product (100), dim_date (365), fact_orders (זהה במספרו ל־silver.orders), daily_sales.
הוכחת ניקוי נתונים: ב־orders_raw שב־Bronze יש 5001 שורות אבל ב־Silver מגיעות פחות מה־Batch — נתוני המקור מכילים בכוונה כמות שלילית, מזהה לקוח חסר, סכום שלילי ומזהה הזמנה כפול; שכבת ה־Silver מסננת את כולם.

7טיפול בנתונים מאחרים (חוק 48 השעות)

ה־Producer שולח בכוונה כ־15% אירועים בני 1–47 שעות (חייבים להתקבל) וכ־5% אירועים בני יותר מ־48 שעות (חייבים לעבור להסגר):

docker exec spark-master spark-submit --master "local[*]" /opt/spark/jobs/show_tables.py silver
תוצאה צפויה: הטבלה silver.order_events_rejected אינה ריקה; בכל שורה lateness_hours > 48 עם הסיבה "arrived more than 48h after event_time". ב־silver.order_events כל השורות עם lateness_hours ≤ 48.

8הדגמת SCD2 (היסטוריית ממד הלקוחות)

  1. ב־Airflow פותחים את batch_etl ← ▶ ← Trigger DAG w/ config.
  2. מדביקים {"snapshot": "day2"} ומריצים. ב־Day 2 יש כ־40 לקוחות שעברו עיר או שינו סגמנט.
  3. כשהריצה ירוקה:
docker exec spark-master spark-submit --master "local[*]" /opt/spark/jobs/show_tables.py gold
תוצאה צפויה: gold.dim_customer גדלה ל־540 שורות — 500 גרסאות נוכחיות (is_current = true) ו־40 גרסאות היסטוריות סגורות עם effective_to מלא. הזמנות ישנות ממשיכות להצביע על הגרסה ההיסטורית — וזו בדיוק המהות של SCD Type 2.

9בדיקות איכות נתונים ו־Great Expectations

docker exec spark-master spark-submit --master "local[*]" /opt/spark/jobs/show_tables.py audit
תוצאה צפויה: audit.dq_results — שורה לכל בדיקה בכל ריצה (בדיקות ה־Bronze כוללות ממצאי WARN על השורות הפגומות שהושתלו בכוונה; בדיקות Silver/Gold כולן passed = true). audit.ge_results — 15 תוצאות Great Expectations לכל ריצה, כולן success = true.
בדיקה שלילית (רשות): שערי האיכות באמת חוסמים — אם בדיקת ERROR בשכבת Silver תיכשל אי פעם, ה־DAG נעצר לפני Gold ושם הבדיקה הכושלת מופיע בלוג המשימה.

10הקבצים ב־MinIO (ה־Lake הפיזי)

  1. פותחים את http://localhost:9001, מתחברים עם admin / password.
  2. מנווטים ל־Bucket בשם warehouse.
תוצאה צפויה: תיקייה לכל Namespace‏ (bronze, silver, gold, audit), ובכל טבלה — data/ (קובצי Parquet) ו־metadata/ (קובצי Snapshots/Manifests של Iceberg).

פתרון תקלות

"network lakehouse not found" — מריצים docker network create lakehouse ואז שוב את שלוש פקודות ה־up.

Airflow עדיין לא מציג DAGs — ממתינים כ־20 שניות אחרי ההפעלה; ה־Scheduler סורק את תיקיית ה־DAGs כל 10 שניות.

המונה של order_events לא גדל — מריצים פעם אחת את streaming_supervisor ובודקים עם docker exec spark-master tail -n 30 /tmp/streaming_ingest.log.

ריצות Spark נכשלות עם Service failed: 500 אחרי ריסטארט של Docker או של המחשב — קטלוג ה־Iceberg עלול לחזור במצב פגום אחרי כיבוי לא נקי. מריצים docker restart iceberg-rest ומפעילים שוב את ה־DAG. אם ה־Job של הסטרימינג נפל בזמן התקלה, streaming_supervisor יפעיל אותו מחדש אוטומטית בריצה הבאה שלו (כל 10 דקות).

פורט תפוס — תהליך אחר במחשב מחזיק את 8090 / 9000 / 9001 / 8181 / 29092; עוצרים אותו או משנים את הפורט המפורסם בקובץ ה־Compose הרלוונטי.

אחרי ריסטארט למחשב — פשוט מריצים שוב את שלוש פקודות ה־docker compose … up -d; כל הנתונים נשמרים ב־Docker Volumes.

כיבוי המערכת

docker compose -f orchestration/docker-compose.yml down
docker compose -f streaming/docker-compose.yml down

הערה: הוספת -v מוחקת גם את ה־Volumes של הנתונים (התחלה נקייה בפעם הבאה). פרטי ההתחברות במדריך הזה הם ברירות מחדל לפיתוח מקומי — מתאימים להדגמה, לעולם לא לפרודקשן.
